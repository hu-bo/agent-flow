# Agent Flow Web Server 逆向重建 Prompt

## 使用方式

将下面的 Prompt 交给具备软件工程能力的 AI Agent，用于在 Agent Flow 单体仓库中从零设计并实现 Web Server。目标是复现现有服务的产品能力、系统边界和运行特征，而不是复制任何已有源码。

---

## Prompt 正文

你是一名资深后端架构师和 TypeScript 工程师。请在一个 AI Agent 编排平台的 monorepo 中，设计并实现面向 Web UI、管理控制台和远程执行节点的 BFF/API 服务。

本任务只允许依据以下技术依赖、架构方案、业务能力和验收标准进行实现。不要寻找、引用、复述或仿写任何既有服务源码；不要假设已有实现细节；应自行完成模块设计、接口契约、数据结构和测试方案。

### 一、目标与边界

服务是平台的统一后端入口，负责连接前端应用、Agent 核心运行时、模型供应商、持久化存储、认证中心和远程 Runner。它需要同时承担：

- 面向浏览器的 JSON API 与 SSE 流式 API。
- 用户认证、身份同步和管理员权限控制。
- 项目、会话、消息、模型配置和任务的管理。
- 普通对话、自治 Agent 执行和显式远程命令三种运行路径的统一编排。
- 上下文压缩、会话记忆和规格化研发工作流。
- 远程 Runner 的注册、心跳、能力发现、任务分发、取消、审批和执行日志持久化。
- 统一错误协议、请求追踪、结构化日志和运行链路观测。

服务不应直接承载前端页面，也不应把具体模型供应商协议泄漏给上层业务。模型调用必须通过统一适配层完成，Agent 规划与执行必须复用核心运行时。

### 二、指定技术栈

- 使用 TypeScript 严格模式、ESM 模块和 ES2022 运行目标。
- 使用 Node.js 作为运行时。
- 使用 Fastify 5 构建 HTTP 服务和插件化生命周期。
- 使用 Zod 定义并校验请求参数、查询参数、请求体和环境配置。
- 使用 TypeORM 连接 PostgreSQL，并以显式迁移维护数据库结构。
- 使用 SSE 提供聊天、Runner 状态和任务事件的实时推送。
- 使用 gRPC 建立服务端与远程 Runner 之间的双向或长连接通信能力。
- 使用 Vercel AI SDK 为主的统一模型适配包，并兼容 OpenAI、Anthropic 和本地模型适配器。
- 使用平台核心包提供 Agent 循环、规划执行、工具注册、检查点、回放和会话状态能力。
- 使用平台压缩包提供自动和手动上下文压缩。
- 使用平台记忆包提供会话记忆写入与召回。
- 使用平台事件包提供结构化日志和 span 级追踪。
- 使用平台工具包提供文件系统、Git 和 HTTP 等工具能力。
- 使用 Vitest 完成协议、路由、运行时分流和关键服务测试。

### 三、总体架构方案

采用清晰的分层架构，各层只能通过稳定契约协作：

1. 应用装配层：负责环境加载、HTTP 服务创建、CORS、数据库、业务服务、路由和退出清理。
2. 路由层：只声明 URL、HTTP 方法、认证要求和请求体类型要求。
3. Handler 层：完成输入校验、身份上下文提取、业务服务调用和响应转换，保持轻量。
4. Service 层：承载领域规则、事务边界、权限隔离和跨模块编排。
5. Chat Turn 编排层：负责单轮对话的准备、消息持久化、取消、重试、记忆记录和规格工作流协调。
6. Runtime 层：负责对话模式判定、核心 Agent 运行时调用、模型流式生成、工具循环和事件映射。
7. Runner 控制层：负责 Runner 注册目录、连接管理、任务调度、审批、取消和执行事件日志。
8. 数据访问层：使用 ORM 实体和仓储持久化领域状态，使用迁移演进结构。
9. 基础设施层：提供认证客户端、模型适配器工厂、SSE、错误模型、日志、追踪和请求上下文。

通过依赖注入式服务容器完成对象装配。业务层不得自行读取全局环境变量或创建数据库连接。所有外部依赖都应可替换，以便测试。

### 四、HTTP 与协议方案

所有业务 API 统一挂载在 `/api` 下。健康检查和 OAuth 登录流程允许匿名访问，其余业务默认要求 Bearer Token。管理员配置接口还必须验证管理员角色。

普通 JSON 响应使用统一 envelope，至少包含业务状态、数据、消息和请求 ID。异常响应需包含稳定错误标识、可读消息、请求 ID，并允许附带结构化详情。无响应体的删除操作可以返回 204。SSE 接口不使用 JSON envelope。

每个请求都要建立请求上下文，包括请求 ID、开始时间、调用来源、当前用户和可选幂等键。响应头应回传请求 ID。统一处理校验错误、业务错误、Fastify 客户端错误、未知服务端错误和未匹配路由。

SSE 必须满足以下要求：

- 使用标准事件流响应头并禁用代理缓冲。
- 定期发送心跳以维持连接。
- 支持结构化事件和明确的结束标志。
- 客户端断开时及时取消订阅并释放资源。
- 聊天流可表达完整消息、文本增量、思考状态、规格文档增量、审批请求、底层运行时事件和错误。

### 五、认证与用户方案

接入外部 OAuth/OIDC 风格认证服务，提供授权地址、注册地址、授权码换取 Token、刷新 Token 和获取当前用户能力。

受保护接口必须校验 Bearer Token，并将远端用户资料同步到本地用户表。用户模型至少覆盖外部用户标识、用户名、展示名、邮箱、头像、角色和状态。管理员能力使用本地同步后的角色进行授权。

不得记录访问令牌、刷新令牌、供应商密钥或 Authorization 头。所有错误日志和追踪属性都必须执行敏感字段过滤。

### 六、模型治理方案

提供两类模型能力：

- 用户侧模型目录与当前会话模型切换。
- 管理侧供应商、凭据、供应商模型、模型 Profile、路由策略和审计日志管理。

供应商配置需要支持不同适配器类型、基础地址、状态和扩展元数据。凭据只能保存安全引用或加密后的秘密，不允许在查询响应中返回明文。

模型 Profile 用于表达业务意图与模型选择策略。路由策略至少支持主模型、候选模型、优先级或回退方式及启停状态。配置变更后应使运行时模型缓存及时失效或刷新。

模型适配层必须隔离不同供应商 SDK 的差异，并统一流式生成、非流式生成、工具调用、推理强度和 Token 限制。调用方只依赖统一模型描述和适配器协议。

所有管理变更应写入审计日志，记录操作者、动作、资源类型、资源标识、请求 ID、变更前后摘要和时间，且避免写入凭据明文。

### 七、项目、会话与消息方案

项目代表一个用户拥有的工作空间，包含名称、根目录和可选默认 Runner。项目根目录与 Runner 的关系必须校验，避免用户绑定无权访问或不存在的执行节点。

会话属于用户，可选属于项目，并保存标题、模型、交互模式、工作目录、消息数、系统提示、最近检查点、绑定 Runner 和规格工作流状态。会话标题可依据首条有效用户消息自动生成。

消息按会话内严格递增序号持久化，保留统一消息内容、角色、类型、时间、父子关系和扩展元数据。支持查询完整会话状态、追加或更新消息、截断历史、删除指定消息及从历史消息重新执行。

所有项目和会话查询必须按当前用户隔离。删除项目时应明确处理其会话关联；删除会话时应处理消息和相关运行状态，避免孤儿数据。

### 八、聊天与 Agent 运行方案

单轮聊天采用两级编排：外层处理会话业务，内层处理运行模式。

外层流程应覆盖：

1. 校验会话归属和模型可用性。
2. 创建或加载会话，并刷新项目工作目录。
3. 规范化文本、附件、推理强度、Runner 偏好和审批信息。
4. 持久化用户消息并构造历史上下文。
5. 召回少量高相关会话记忆，同时过滤内部诊断信息。
6. 调用运行时并把事件实时转成统一聊天事件。
7. 持久化最终消息和必要的中间状态。
8. 将有效用户与助手内容写入记忆。
9. 支持按用户与会话取消正在执行的轮次。

内层运行时根据语义选择三种模式：

- 简单寒暄或确认类消息走直接模型对话，优先流式输出，必要时回退到非流式生成。
- 规格模式或具有执行意图的普通请求走自治 Agent，通过核心运行时完成规划、步骤执行、工具调用、验证、检查点和事件回放。
- 带显式远程执行指令的消息走 Runner 模式，将命令及参数转成受控任务，而不是直接在服务进程执行。

自治运行过程中要把会话、步骤、工具、审批、检查点和 Runner 事件实时映射给前端，并去重事件。应同时生成适合用户阅读的思考活动与阶段摘要。若核心运行时没有产生可展示结果，可使用模型结合运行上下文生成有限轮次的回退回答。

模型工具循环必须设置明确的最大轮次和输出 Token 上限。推理强度至少支持低、中、高三级，并映射到不同资源预算。取消信号必须贯穿模型、工具、核心运行时和 Runner 调用。

### 九、上下文压缩与记忆方案

支持手动、自动和模型切换触发的会话压缩。压缩前根据角色、时序和重要性为消息赋权，保留关键系统约束、近期用户意图、重要工具结果和未完成任务状态。

压缩结果应形成可继续对话的摘要或重写上下文，并原子替换会话消息状态。压缩服务需要返回压缩前后规模、触发方式和结果摘要等可观测信息。

记忆能力采用统一服务接口。每轮开始按当前问题召回有限数量的会话记忆；每轮结束记录有价值的用户与助手内容。内部错误诊断、运行噪声和敏感信息不得进入长期记忆。

### 十、规格化工作流方案

会话支持自由对话模式和规格模式。规格模式按“需求、设计、任务拆分”三个阶段推进，每个阶段都需要生成结构化文档、持久化当前状态，并等待用户确认后进入下一阶段。

需求文档应明确背景、目标和需求；设计文档应给出多个可比较方案；任务文档应区分必做与可选任务，并形成可执行、可验证的任务清单。

系统需要从助手输出中识别并保存阶段文档，通过流式事件向前端推送文档增量。阶段确认时应校验当前文档完整性。任务文档还要执行严格格式与语义校验；若生成结果不合格，可以构造纠错上下文进行有限次数自动重试。

### 十一、任务服务方案

提供独立于聊天请求生命周期的任务抽象，任务类型至少包括聊天、工作流和压缩。任务记录需包含会话、可选模型 Profile、状态、重试信息、最近检查点、输入提示、输出和错误。

任务状态至少覆盖等待、运行、暂停、完成、失败和取消。支持创建、列表、详情、暂停、恢复、取消和重试。状态转换必须验证合法性，并通过事件序列记录创建、更新、日志、完成、失败和取消。

任务事件支持按游标补拉和 SSE 实时订阅。执行应使用取消控制器，避免重复调度同一任务。服务重启后的持久化恢复策略应与核心运行时检查点和回放能力衔接。

### 十二、Runner 控制平面方案

远程 Runner 是用户工作空间中的受控执行节点。控制平面需要实现：

- 为用户签发、轮换和撤销 Runner 注册令牌，数据库只保存不可逆摘要和安全前缀。
- Runner 通过 gRPC 携带令牌注册并定期心跳。
- 保存 Runner 的在线状态、主机信息、操作系统、架构、Shell、路径规则、工作区根目录、可用命令、执行引擎、隔离等级和容量指标。
- 根据用户归属、在线状态、能力、工作区、执行引擎和剩余容量筛选或选择 Runner。
- 向前端实时推送 Runner 上下线和状态变化。
- 提供不同平台 Runner 安装包的下载信息，并在构建下载包时注入服务地址和一次性或用户级注册信息。
- 允许用户浏览授权 Runner 的根目录和目录内容，但所有路径访问必须受 Runner 能力与工作区边界约束。
- 支持项目默认 Runner、会话绑定 Runner 和单次请求优选 Runner。

Runner 任务分发必须具备执行 ID、尝试次数、截止时间、最大输出大小、事件续传游标、分发确认、取消确认和终态。执行及其事件日志必须持久化，以支持服务重启后的恢复、重派发、超时终结和事件去重。

Runner 工具至少覆盖受控文件读取与修改、目录与搜索、Git 状态与差异、补丁应用和 Shell 执行。工具输入必须经过结构化校验，命令不得通过字符串拼接绕过参数边界。

### 十三、风险审批与沙箱方案

执行前根据工具类型、路径、命令和操作语义评估风险。只读文件与 Git 查询通常可视为低风险；文件写入、补丁、Git 修改和可能改变系统状态的 Shell 命令应视为高风险。

高风险操作必须满足以下一种条件才能分发：

- 当前请求携带有效的一次性审批票据。
- 用户已对指定 Runner、项目或会话授予仍有效的持久审批。
- 可信内部流程明确传入经过验证的风险许可。

审批必须绑定用户、Runner、作用域和请求上下文，防止跨用户或跨任务复用。支持“一次允许”和“持续允许”，并允许用户查看和撤销持久授权。审批决定、使用时间和撤销时间需要持久化。

Shell 风险判断不能只看命令名称，还要识别重定向、子命令、变量展开、Shell 包装器和常见变更语义。工作目录和所有路径必须是绝对、规范化且位于授权工作区内。Runner 需要声明 host 或容器执行引擎；容器模式应支持镜像、挂载和资源限制等沙箱配置。

### 十四、持久化模型方案

PostgreSQL 至少需要覆盖以下领域数据：

- 本地用户。
- 模型供应商、供应商凭据、供应商模型、模型 Profile、路由策略和管理审计。
- 项目、聊天会话和聊天消息。
- 核心运行时会话、检查点和回放事件。
- Runner 注册令牌、Runner 状态、审批授权、执行记录和执行事件日志。

对高频查询建立适当索引，包括用户会话更新时间、项目会话更新时间、会话消息序号、Runner 用户与状态、Runner 最近心跳、执行任务标识、执行状态和事件序号。

使用数据库唯一约束保证会话内消息顺序、项目工作区唯一性、Profile 路由唯一性和 Runner 执行事件幂等。时间字段统一使用带时区时间。灵活的运行时状态和事件载荷可使用 JSONB，但核心查询字段必须结构化存储。

启动时检测并终结无法继续的中断运行时会话，同时恢复尚可重派发的 Runner 执行。恢复动作必须写入结构化日志。

### 十五、可观测性与可靠性方案

为每个请求、聊天轮次、Agent 任务和 Runner 执行建立可关联的请求 ID、session ID、task ID 和 execution ID。

使用结构化日志记录关键生命周期事件、状态、耗时、事件数量和失败摘要。开发环境允许更详细日志，生产环境默认使用信息级别。运行日志支持写入文件或可替换 sink。

错误记录应保留足够诊断信息，包括失败阶段、最后事件、步骤失败、Runner 错误和最后输出摘要；同时必须递归过滤名称中包含密钥、令牌、秘密或授权信息的字段，并限制超长字符串、数组和对象大小。

所有长连接、定时器、订阅、等待队列和取消控制器都必须在完成、错误、超时、客户端断开或服务退出时释放。任务分发需要处理重复确认、重复事件、乱序事件、Runner 离线、执行超时和服务重启。

### 十六、配置与部署方案

使用环境变量配置 HTTP 监听地址与端口、运行环境、默认模型、CORS 来源、PostgreSQL 连接、认证服务地址与应用名、Runner 对外服务地址、gRPC 地址与端口、Runner 下载基础地址及可选安装包模板目录。

环境配置必须在启动阶段一次性解析和校验，转换成类型安全的内部配置。支持从当前工作目录、应用目录或仓库根目录加载环境文件，但已存在的进程变量优先。

提供开发监听、类型检查、测试、构建和生产启动脚本。提供容器镜像和本地 PostgreSQL 编排方案。生产启动时先初始化数据库和服务容器，再监听 HTTP 与 gRPC；退出时按反向顺序关闭入口、连接和后台任务。

### 十七、测试与验收标准

至少完成以下测试：

- 环境配置默认值、非法值和 CORS 多来源解析。
- 匿名、登录用户和管理员的路由权限边界。
- 统一响应、校验错误、404、未知错误和请求 ID。
- 项目、会话和消息的用户隔离及关键生命周期。
- 聊天 SSE 的事件顺序、结束标志、取消和客户端断开。
- 简单对话、自治执行、规格模式和显式 Runner 指令的运行时分流。
- 模型流式失败后的非流式回退，以及自治运行无展示结果时的有限模型回退。
- 消息重试、历史截断、记忆召回和压缩后的会话一致性。
- 规格工作流三个阶段的文档捕获、确认、校验和自动纠错。
- 模型管理变更、路由缓存刷新、凭据脱敏和审计日志。
